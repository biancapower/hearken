# 0002. The stack

**Context.** Hearken is a server-rendered Rails app whose player page installs as a PWA (0001). Bianca's planning record for Book by Book (decision 0004 in their planning repository, approved 2026-10-12) settled the Rails 8 defaults one at a time; Hearken carries those choices where they apply. Spike 17 tested the player architecture in a throwaway Rails app and found that no JavaScript build step was needed.

**Decision.**

1. **Rails 8.1 on Ruby 4.0.** The current stable releases (Rails 8.1.4, Ruby 4.0.7 on 2026-10-18); Rails is Bianca's first-preference stack.
2. **PostgreSQL.** Bianca's choice for Hearken over a SQLite recommendation, 2026-10-18; it leaves room for more than one process and more than one user without a migration later.
3. **Hotwire (Turbo) and Stimulus, through importmap and Propshaft.** Server-rendered pages with small controllers and no bundler, as in 0004; the spike's player needed nothing more.
4. **Tailwind for the app's chrome,** using the standalone binary, so no Node. The player's own layout may use a plain stylesheet if Tailwind fights it, as 0004 did for the shelf.
5. **Rails 8's PWA manifest and service worker,** served from `app/views/pwa`, with no service worker library. The spike's offline design (the Cache API holding downloads and answering range requests) was a few dozen lines on this base.
6. **Solid Queue** for feed refreshes as recurring jobs, as in the spike. **Solid Cache**, the default, costs one table until it is used.
7. **RSpec with FactoryBot** for tests, generated without Minitest (`--skip-test`), as in 0004.
8. **Playwright for system specs.** Auto-waiting suits the no-retries policy. Whether through the Capybara Playwright driver or `playwright-ruby-client` directly is decided at the first system spec, as in 0004.
9. **RuboCop (rails-omakase), Brakeman and bundler-audit as generated,** run with the suite by `bin/ci`, which GitHub Actions runs on every pull request.
10. **Skip Action Text, Action Mailbox and Jbuilder; keep Active Storage, Action Mailer and Bootsnap,** as in 0004. Active Storage is the likely home for audio the user uploads; the spike found its proxy already answers range requests.

**Where Hearken differs from 0004.**

- **Deployment:** 0004 planned Kamal to Bianca's own machine over Tailscale. Hearken 0.1.0 runs on that machine under a systemd unit behind `tailscale serve`, as the spike did, which needs no container registry or Docker. The generated Kamal config and Dockerfile stay unused until public hosting is decided.
- **Solid Cable:** generated by default and kept, but 0.1.0 plans no live updates between devices, unlike the bookcase's phone-to-TV link.
- **No Open Library gem, and a new untrusted input:** feeds. Their contents and, later, user-entered feed URLs carry the security rules in `CLAUDE.md`.

**Open.** How the pure client-side modules (queue rules, transcript cue lookup, offline outbox) are unit-tested. The spike used `node --test`, which adds Node to the development and CI toolchain though not to the app. A 🔴 dependency decision, made at the first issue that adds such a module.

**Alternatives.** SQLite (simpler on one host; set aside by Bianca's choice of Postgres). A JavaScript framework for the player (set aside: the spike's player worked with Stimulus and no build). Minitest (the Rails default; RSpec is what Bianca knows and what 0004 chose). Kamal for 0.1.0 (more moving parts than one machine on a tailnet needs).

**Reasons.** One stack across Bianca's Rails projects, so what is learned carries over. Each choice above is the Rails default or was tested by the spike, except Postgres and RSpec, which are Bianca's.

**Consequences.** `rails new` runs with `--database=postgresql --css=tailwind --skip-test --skip-action-text --skip-action-mailbox --skip-jbuilder`. Adding RSpec, FactoryBot and Playwright are dependency changes covered by this record.
